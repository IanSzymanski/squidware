# Editor architecture

`App.tsx` creates one editor store and provides it to the extracted shell. No editor state is global, so another editor can use its own store in a test or future window. The canonical `.squid` schema is version 2, with pictures and adjacent moves stored separately; v1 imports migrate through the shared codec. The domain engine has no React, browser storage, or desktop bridge dependencies. See [the schema contract](schema-v2.md) for command identity and timing semantics.

## State and subscriptions

`src/editor/state.ts` separates named reversible project history, active set and selection, playback, transient interface state, and file-session state. Audio object URLs, saved revisions, menus, selection and the playhead never enter the project or undo history.

`useEditorSelector` uses React's external-store subscription API. Selectors return a primitive or an existing immutable object reference; do not construct a new array or object on every snapshot. `subscribeSelector` also accepts a custom equality function for non-React subscribers. A UI setter publishes only when its value changes. A synchronous command publishes a single completed state to subscribers, including commands that update the project, selection and playback together.

`EditorField` and `EditorTimeline` subscribe to playback counts. The shell subscribes to project, selection, interface properties and an arrival boolean, so normal frames within a transition do not rerender the shell. `usePlaybackController` owns the animation clock, metronome and audio synchronization; it reads the starting count directly from the store. The active set changes at transition boundaries.

Workspaces, dialogs, shared controls and the main editor controller are extracted into `src/editor`. File operations remain in `useEditorController`, where the browser inputs, desktop bridge and object URL lifecycle belong. `useCommandController` binds native menu actions and browser shortcuts using current store state, avoiding stale event-handler closures. Native text-input undo/select-all behavior is preserved.

## Commands and extension boundaries

Every project mutation enters `store.dispatch(commandId, arguments)`. `src/editor/commands.ts` declares the argument types, stable IDs, names, descriptions, descriptive argument metadata, shortcut labels, enablement and handlers. `commandMetadata` can populate a future palette or scripting client; the help dialog and command-aware button tooltips already reuse it. TypeScript callers get checked argument shapes. Enablement and the domain validators reject invalid timing, navigation, field coordinates, roster references and project limits at runtime.

Control help uses the shared `Tooltip` component and `HelpButton`. The help dialog, menu hints and command tooltips format current registry bindings through `commandKeycaps`; context-specific effects and disabled explanations belong to their controls. See [accessible control help](tooltips.md) for interaction rules and verification.

For example:

```ts
store.dispatch('set.update', { index: 1, update: { counts: 64, tempo: 144 } });
store.dispatch('selection.transform', { index: 1, ids: ['performer-id'], options: { dx: 0.625 } });
store.dispatch('history.undo');
```

Add a command by defining its arguments in `CommandArguments` and its metadata, enablement and handler in the registry. Project handlers call the store's private command context; components cannot pass arbitrary mutation callbacks into the store. Keep calculations in `domain.ts` and side effects in controllers. `file.open`, `file.save` and `file.save-as` use registered per-editor controller handlers. Both synchronous and asynchronous controller failures return `false` and surface a notification. A failed project validation records no edit.

`setValue` is restricted to non-project slices and is appropriate for session-only controls and playback frames. Shared editing operations, menus and shortcuts use commands. `project.load` validates before replacing history and resets selection, playback and draft epoch. Keyed set controls reset local numeric drafts when the current set or loaded project changes, including loading the same project ID again.

History stores reversible patches with named synchronous transactions and explicit preview commit/cancel boundaries. Equal values are no-ops without project-wide serialization. The engine validates metadata, sections, performers and changed geometry before publication; unchanged positions maps retain their prior validation under the immutable sharing contract. Imports, initial state and file output still validate the complete project. Revision IDs support saved-state comparisons through undo/redo, and deferred recovery serializes only committed projects. History retains up to 80 actions or 16 MiB of estimated payload, always keeping the latest action; the History panel discloses expiry and the large-action exception. See [the history contract](history.md) for API and field behavior.

## Separate 3D window

The 3D window (#181) is an about:blank window that the editor fills through a React portal, so it reads the same store as the field with no state copy or IPC sync. `Mirrored3D` renders the current scene for both the inline 3D view and the window: `useFieldScene` chooses a preview, the editable set or the sampled playhead (one shared sample per project and count), rehearsal focus scopes it, and an uncommitted 2D drag reaches it through a per-editor `moveDrafts` channel. A later split view (#41) should reuse the same component. `Stage3D` takes its document, clock, pixel ratio and `ResizeObserver` from its own window and stops drawing while that window is hidden. While the window is open it is also a frame source for playback (`frameSources.ts`). A window's frame runs a playback frame only if no other window has run one since that window's previous frame, so windows painting in the same vsync, or alternately at other phases or rates, never publish twice for one frame. The editor is the clock while it paints normally. A 3D window's frame runs only while the editor counts as throttled: its smoothed frame interval is at least 400 ms (each interval, capped at 800 ms, moves it a quarter of the way, or half while stopped), it has painted nothing for more than four smoothed intervals (67 ms at 60 Hz), or, after such a silence (a stop), it has not yet painted two frames in a row less than 400 ms apart. Chromium gives a minimized, covered or hidden editor about one uneven frame a second, or none: now and then a frame comes 240 ms after the previous one, but in the measured runs never two in a row. So the 3D window drives at its own rate, through early editor frames and through 3D frames that cluster in part of an editor gap; one early frame does not end a stop (it used to, and when a minimized editor's first throttled frames came 600 and 250 ms apart the 3D window then waited four smoothed intervals, about a second). Two frames in a row less than 400 ms apart also bound the smoothed interval by the longer of the two, so an editor painting faster than 2.5 frames a second again takes the clock at its second such interval, whatever its history: within three frames at 60 Hz, and at once after a throttled history that used to take five to eight frames of a heavy show to decay. There is no frame count to reach and nothing to reset. A new playback loop (play, resume, or a restart of the playback effect after an edit) leaves the clock where it was. If the editor ran the last frame, its silence counts from the restart, so a pause never looks like a stop. If a 3D window ran it, that window runs its next frame, so a stopped editor resumes at the first 3D frame and a restart skips no 3D frame; the editor's first frame after the resume measures the interval across the pause, a long one after any real pause (it is capped at 800 ms), so a 3D window keeps driving while the editor stays throttled, and a shown editor painting faster than 2.5 frames a second takes the clock at its third frame after the resume. It runs from that frame, or from its fourth when a 3D frame came between its second and third, since a window's frame runs only if no other window ran one since its previous frame. In simulations of the popout-3d sequence (a hidden-editor playback, a pause, then the editor shown painting every 270 or 350 ms beside a 3D window painting every 200 ms), the 3D window now runs 3.5 or 4.5 frames after the resume on average (at most five); the throttled history used to keep it driving until about the editor's fifth or seventh frame (up to its ninth: 1.3 or 2.3 s on average, up to 2.9 s), publishing from each 3D frame and re-rendering both windows. A shown editor painting faster than 2.5 frames a second keeps the clock however fast the 3D window paints. The popout-3d suite places the editor and the 3D window side by side (a covered window is occluded on macOS and paints nothing), where the software-rendered maximum show paints the editor three to five times a second and the 3D window three to seven; it checks that no window's frame runs playback after another window ran one since that window's previous frame, which any double run breaks, and that playback publishes about once per painted editor frame from the editor's first frame. Such an editor also keeps the clock through its occasional long frames (a heavy show on a slow host paints every 250-300 ms with frames of 700 ms between): only a silence of four of its frame intervals hands frames to the 3D window, since filling in each long frame would render both windows more often than the editor paints. An editor averaging slower than 2.5 frames a second counts as throttled even when shown, so a faster 3D window then publishes once per 3D frame, rendering both windows each time: such an editor cannot show smooth playback, and the 3D window can (two of its frames less than 400 ms apart give it the clock until its next long frame; an editor at 450 ± 80 ms beside a 3D window at 10 frames a second does that about once in 12 seconds in simulation, holding the 3D window for one editor frame). The measured cost is small: on a software-rendered host with 500 performers, a shown editor painting 0.8-2.6 frames a second beside a small 3D window still published about once per editor frame, with no rise in renderer CPU, because both windows share the renderer's main thread and the GPU process, so the 3D window rarely outpaces such an editor. Window visibility, focus and occlusion are not used: the editor stays visible to the page while background throttling is off, Electron reports no occlusion (main could report minimize and hide, which leave a covered editor, the common case on one monitor, to the rate rule anyway), and a writer watching the 3D window on a second display usually keeps focus in the editor, so a focus rule would hold the 3D window to a slow editor's rate. With no 3D window open, playback frames are plain `requestAnimationFrame` calls. The inline field shows a placeholder, so only one renderer exists. `ui.popout3d` is `unavailable` without the desktop bridge, which hides the button and palette entries and leaves the `Shift+T` binding inert: it matches no key and conflicts with nothing, and assigning its key to another command in the browser unbinds it there.

Main allows exactly one window request: frame name `squidware-3d-preview` with the URL `about:blank`. It denies external URLs, other names, form posts and a second preview (which focuses the existing one instead). The window is sandboxed with context isolation, no Node integration, no webviews and no preload, so it has no desktop bridge. It inherits the editor's CSP (the editor also copies the policy and stylesheets into its head), cannot open windows or navigate, and closes when the editor reloads or crashes. Main validates the saved geometry against the connected displays before every open; the renderer only stores what main reports after moves and resizes. Display ids are int64 values that Electron reports as doubles; X11 ids derived from a monitor's EDID exceed 2^53, so any integer id is kept, identical monitors that share a rounded id resolve to the one under the saved window, and an unusable id drops only the id, not the geometry. A window closed by the renderer holds main's single slot until its native window is gone (usually under 0.2 s), so a request made in that interval is denied and the editor retries it for up to 2 s before reporting that the window could not open.

## Verification

File state uses a saved revision or `null`, separate pending drafts, and an in-flight operation guard. New/recovery loads stay unsaved; successful file opens establish a baseline. Save completion records its captured revision only within the same project epoch. Dirty selectors also drive native close protection directly. See [file and draft behavior](FILE_STATE.md) for cancellation, failure, concurrent edits and browser download semantics.

`src/editor/store.test.ts` exercises selective notifications, compound-command consistency, undo/redo, project limits, runtime navigation arguments, playback editing guards, roster and formation edits, file-controller registration, save/reopen compatibility, export data, recovery and sync/async error handling. The Electron workflow QA scripts exercise the real rendered application and desktop bridge with isolated test files and dialogs. Run the domain/editor tests, desktop tests and production build after changing these boundaries.
