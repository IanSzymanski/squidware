# Keyboard and readable editor controls

The 2D field uses one roving Tab stop. Tab enters at the last focused performer, or the first performer when there is no remembered focus. The next Tab leaves the field. Arrow keys focus the nearest performer in that direction without editing or selecting; Page Up/Down walks the roster, including overlapping dots, and Home/End reaches its boundaries.

Enter/Space selects the focused performer. Shift+Enter/Space adds or removes it. Alt+arrows nudges the selected group using the preference increment (default one 8-to-5 step, 0.625 yards); Shift+Alt+arrows uses the fast increment (default four steps). Position edits remain blocked during playback/between-set previews. Space on a standard button activates that button; it does not trigger the global playback shortcut. Form inputs retain their normal editing keys.

The timeline’s problem row is also one Tab stop. Left/Right move between markers, Home/End reach the ends, and Enter/Space goes to a finding or opens a group’s list (Up/Down/Home/End inside; Escape returns to the marker, also in focus mode or over a tucked-panel overlay, and Tab closes the list and continues from the marker, as from a menu button). Choosing a finding keeps focus on the row’s marker even when the review regroups it. The row restores focus only in the update that removes the focused marker or list, or, after a recheck of the focused marker’s moves empties the row, when markers come back, unless a key, click or focus change came first or those moves finished with the row still empty. A row emptied otherwise, such as a count window scrolled past every finding while other moves are checked, lets focus go, and markers that return later never take focus back. Markers and the ⚠ count badge are 24 × 24 px targets named by problem type, performers and whole count; a group’s visible size badge starts its name, so an abbreviated **12k** is named “12k · 12345 spacing problems · …”. Timeline Tab order follows set order: View, the Show-wide problems badge, any rehearsal marks on the ruler, the opening set, each later set, the problem row, then the playhead.

Focus has a square outline, distinct from the circular selection ring. The focused performer exposes label, optional name, section and drill coordinates. Focusing outside a zoomed viewport brings the performer into view. Static SVG/print drawings do not introduce interactive Tab stops. The field keyboard hint and command help describe the same movement modifiers. The hint is always the field's accessible description; it is drawn at the bottom of the field only after a key press inside the field (never after pointer focus), and the field status line steps aside while it shows. With **Show hints** off it stays an accessible description only; Help lists the same keys.

Editor chrome uses at least 11-pixel type, with 12-pixel explanatory text and 13-pixel form inputs. Muted text is darker on the existing light surfaces. Focus outlines, selected-set checks, pressed view/formation controls and error text provide cues beyond color. Disabled controls, including primary and danger actions, use a muted background and dashed borders rather than fading the whole control. The field legend scrolls at extreme section counts. Print typography is unchanged.

## Repeatable checks and scope

Build, then run `pnpm test:accessibility`. It loads a 500-performer, 128-set production into the actual sandboxed Electron renderer using isolated files and controlled native dialogs. Real Tab/Shift+Tab, arrows, roster keys, selection, nudges, text input and standard button activation drive the workflow. It checks every performer, overlapping dots, off-viewport focus, native Save As, Cast/Show review, a read-only transition, recovery to an editable set, and coordinate export. It also checks 125% UI zoom and accessible button names from Chromium's accessibility tree. A separate timeline block checks Tab order across all 128 sets of the loaded production (the expected count comes from the project, not the observed order), the problem row's single stop, 24 px targets, names with their visible badges (label in name), ARIA references and popup states, in-window help, and an open group list against the accessibility tree and the text audit.

Computed-style audits cover Design, Cast, Show, settings, export, read-only preview and enlarged UI text. They check a minimum 11-pixel declared size and 4.5:1 contrast for rendered HTML text against composited solid backgrounds, including placeholders and opacity. SVG artwork, disabled controls and system menu options are excluded. This evidence is bounded; it does not certify screen readers, every graphics device, or all platform settings. The existing writer/platform and representative-hardware gates remain separate. Dense SVG performer labels and timeline zoom remain tracked by #20 and #31.

The implementation follows [W3C keyboard focus guidance](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/) and uses the [WCAG contrast calculation](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html). The production keyboard check runs in Linux CI; actual macOS/Windows assistive-technology walkthroughs still need separate evidence.
