# Asynchronous recovery

Desktop recovery uses fixed preload verbs and a main-process service. Only the production window's main frame at the application URL can invoke them. The renderer receives opaque session/version IDs and cannot choose directories, filenames, IPC channels or filesystem primitives. Recovery lives in `app.getPath('userData')/recovery`; explicit project saves continue to use approved file dialogs independently.

Committed changes debounce for 700 ms. Electron structured-clones the project once for IPC, then a Node worker validates it with the shared v2 codec, serializes it and performs asynchronous I/O. JSON serialization and recovery filesystem work are outside both the renderer and main event loops. IPC structured cloning still has a renderer cost. Text/color drafts and unfinished transactions are not written. Undo to revision zero is a committed change and is recovered too.

Each renderer session has a main-generated lease. A separate increasing request sequence orders writes, because undo can decrease the project's revision. Replayed sequences are rejected; an old lease cannot write after a new session begins. At most one worker write and one latest pending project are retained. Superseded pending requests resolve as stale. File dialogs do not block recovery.

Copies are immutable UUID-named envelopes containing a canonical v2 project, its SHA-256, creation time, source and revision. A complete temporary file is synced and atomically renamed before it becomes visible. Older valid versions are removed only after the new copy is durable. Restart scans validate individual envelopes rather than depending on a mutable catalog; partial temporary files never become recoverable versions. Corrupt originals remain untouched and produce a notice. The renderer cannot read a path by submitting a version ID.

Retention keeps the latest 20 valid copies or 100 MiB across productions, retaining at least the newest valid copy. Preserved unreadable originals and raw legacy sources are outside automatic version deletion. Migration first persists the exact legacy text in a hash-named original file, then validates/migrates it with the same codec. Successful migration has an idempotent marker; only durable success permits removing the legacy localStorage key. Unreadable sources remain in both locations.

Startup offers a dated chooser. It never replaces a production the user edited while storage was opening. Restoring a copy resets the project file destination, marks it unsaved and requires Save As. Version selection checks for intervening edits before applying an asynchronous read and refuses replacement during a pending file operation. Recovery's status and errors remain separate from the [explicit project file and draft state](FILE_STATE.md).

Browser previews use IndexedDB structured clones and transactional retention of 20 copies. They remain subject to browser quota and are not the desktop storage backend.

## Validation

`pnpm test:desktop` covers native sender restrictions and fixed targets, replayed/out-of-order sequences, expired leases, decreasing undo revisions, burst coalescing, interrupted/failed writes, unavailable storage, legacy migration, integrity checks, retention and maximum-size worker restart. `pnpm test:recovery` runs the actual production renderer, preload and main handlers in two fresh desktop processes using an isolated profile. It verifies migration, editing during recovery, an exact maximum-size restore/save, and selecting an older production. CI runs this on Linux; the fulfilled-release package workflow runs it on Windows, macOS and Linux. The native smoke test also round-trips a project through the recovery worker, including packaged module resolution.

The recorded host run uses a 500-performer, 128-set UUID fixture with maximum-length notes and long coordinate precision: 6,186,598 UTF-8 bytes, exceeding 5 MiB. Twenty store edits run with the production React renderer while recovery is in flight. No project JSON serialization or localStorage write occurs in the renderer during that window. Raw command durations and 16 ms timer intervals are in [the measurement record](performance/recovery.json). These measure one Windows host and include instrumentation overhead; they do not qualify school hardware or claim an end-to-end editing budget. Issues #10 and #11 still track renderer costs.
